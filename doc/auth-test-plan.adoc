= Cladone G.O. Gate One — Authentication test plan
:toc:
:toclevels: 3
:icons: font

== 1. Purpose and scope

This plan covers the authentication of Gate One and of the OIDC IAM:

* Gate One only knows **OIDC/JWT**; it loads no provider plugin.
* The IAM is an **OIDC/JWT issuer**: it federates Google, applies the policy
  (roles, tenant, audiences), then re-issues its own signed JWTs.
* The IAM's internal contract is `IdentityAdapter`: a single contract, several
  implementations per protocol (OIDC, then LDAP/mTLS/API key), a single loading
  mechanism for plugins.
* The degraded mode is **fail-fast per tenant only**: the failure of one provider
  must never block the other tenants.
* The **invalid token** and **provider/network unavailable** errors are
  distinct, with different HTTP statuses.

Out of scope for V1:

* SAML and LDAP (V1.1/V2);
* PASETO;
* real calls to Google in CI (fake Google + staging);
* mTLS/API key on the Gate One side (V1.1, via the IAM).

== 2. Behaviour decisions

=== 2.1 Fail-fast per tenant

Configuration loading remains **globally strict**: a grammar error, an unknown
provider, a duplicate ID or an inconsistent route refuse loading or reload. On the
other hand, a provider's **availability** is isolated per tenant.

[cols="1,3,3,2"]
|===
| Situation | Gate One | Routes of the affected tenant | Other tenants

| Invalid config
| `core.Load` fails; on reload, the previous generation remains active
| No change
| No change

| Provider down at startup
| The process starts; the provider is marked `degraded`
| Operations that require the provider respond `502 authentication_unavailable`
| Start normally

| Provider down at runtime
| The provider becomes `degraded`; health and logs expose the state
| Local sessions still valid: `200`; new login: `502`; MCP with JWKS key in cache: `200`; unknown `kid`: `502`
| Unchanged

| Reload with provider down
| The new generation is built; the faulty provider is `degraded`
| Routes updated, faulty provider in `502`
| Updated normally

| Reload with invalid config
| Reload refused; the previous generation remains active
| No change
| No change

| All providers down
| The process stays alive; `/readyz` may go `503` if no public route can be served
| `502` on authenticated routes
| Possible public routes unchanged
|===

Rules:

* A provider in `degraded` does **not** mean that all its routes respond
  `502`. Sessions already issued remain valid locally until their
  expiration; only operations that require a call to the provider
  fail in `502`.
* Startup must not be blocked by an unavailable provider, unless the
  configuration itself is invalid.
* On reload, a provider whose configuration has changed and whose construction
  fails is `degraded`; the old provider is not reused for a
  different configuration.
* The instances of the previous generation are closed after draining.

Health:

* `/healthz`: liveness, `200` as long as the process responds.
* `/readyz`: `200` if Gate One can serve at least one route; `503` if no
  provider is ready and no public route exists.
* `/__gate-one/health/providers` (admin): JSON state per provider.
* `gate-one doctor`: one status per provider, without starting the server.

=== 2.2 Error classification

[cols="2,2,1,3"]
|===
| Condition | Internal error | HTTP | Response

| Missing, malformed, invalid signature, expired token, future `nbf`, wrong `iss`/`aud`
| `ErrUnauthenticated`
| `401`
| JSON or MCP challenge; login redirection for frontend navigation

| Insufficient MCP scope
| `ErrInsufficientScope`
| `403`
| `WWW-Authenticate: Bearer error="insufficient_scope"`

| Identity conditions (`roles`, `scopes`, `claims`, `user`) not satisfied
| `ErrPolicyDenied`
| `403`
| `forbidden` page/JSON; no automatic login redirection; "log out and change account" action on the page (interactive provider)

| Login host root with an allowed `returnTo`/`continueUrl`
| `302`
| Redirection to the app, query preserved (`mode`, `oobCode`, `lang`…), routing parameters removed

| Root with action payload (`mode`, `oobCode`, `key`, `code`, `state`, `token`) without return
| `400`
| "Incomplete link" page: cause, received parameters (names only), `defaultAppUrl` button, correlation reference

| Bare root (`https://login.<domain>/`)
| `302`
| Redirection to `defaultAppUrl` (operational fallback)

| JWKS unreachable, timeout, TLS, malformed response
| `ErrProviderUnavailable`
| `502`
| `authentication_unavailable`, never a login redirection

| OIDC discovery unreachable at login
| `ErrProviderUnavailable`
| `502`
| `authentication_unavailable`, never a login redirection

| Revocation store in error
| `ErrProviderUnavailable`
| `502`
| Fail-closed; never `401`

| Unknown provider, invalid config, duplicate ID
| loading error
| — | Startup/reload refused

| Public route + `auth.provider` | loading error | — | Startup/reload refused

| Rate limit / quota
| `ErrRateLimited`
| `429`
| Existing proxy response
|===

Rules:

* `401` = the client can fix its request (missing/invalid/expired token).
* `403` = the client is authenticated but not allowed.
* `502` = Gate One cannot verify; the client cannot fix it.
* A `502` must **never** offer a login: guaranteed loop.
* An MCP `401` carries `WWW-Authenticate`; an MCP `502` does not.

=== 2.4 Implementation impacts required by these tests

* `providerRegistry` with `starting`, `ready`, `degraded`, `closed` states.
  `proxy.New` builds each provider independently; a discovery failure
  does not return a global error, it marks the provider `degraded`.
* `Gateway.ProviderStatus()` and `ProviderHealth()` for `/healthz`,
  `/readyz`, `/__gate-one/health/providers` and `doctor`.
* `classifyingKeySet` around `go-oidc`: distinguish
  `ErrUnauthenticated` (signature, claims, token) from
  `ErrProviderUnavailable` (JWKS HTTP, timeout, TLS, malformed response).
  An unknown `kid` with a successful JWKS refresh and an invalid token remains `401`;
  an impossible refresh becomes `502`.
* `ErrProviderUnavailable` mapped to `502 authentication_unavailable` in the
  proxy and the MCP handler; `WWW-Authenticate` only on `401`.
* `authCache` keyed by `provider.ID()` and not `provider.Name()`.
* Session and OIDC transaction cookies parameterised per provider.
* `loginHandlers` indexed by host, `serveMCPProtectedResourceMetadata` by
  access unit/provider.
* `Reloadable`: new generation built with degraded providers,
  swap, draining, then `Close()` of the old providers.
* `Gateway.Close()` closes the stores, the HTTP clients and the providers.

`internal/testutil/auth.NewFakeGoogle(t)` returns an `httptest.Server` with:

| auto-consent; `state`, `nonce`, PKCE, `login_hint` parameters

* `RotateKey`, `RetireOldKey`.

Each toggle is a public field protected by a mutex, reset to zero by `t.Cleanup`.

=== 3.3 Test IAM

Two modes:

* **in-process**: the real IAM code, SQLite in `t.TempDir()`, fixed keys,
  injected clock. Recommended for integration tests.
* **minimal fake**: a server that only serves discovery/JWKS/token, for the
  Gate One unit tests.

The test IAM exposes `Down`, `FailJWKS`, `FailToken`, `RotateKey`, `Slow`,
`Revoke(sid)`.

=== 3.4 Fake `IdentityAdapter`

`pkg/identityadapter/conformance/testadapter` implements the contract with
configurable steps:

* `Start` → `Redirect`, `Challenge`, `Form` or `Result`;
* `Continue` → `Result` or classified error;
* `Enrich` optional;
* `Health` with timeout/500.

It is used to test the conformance suite itself, then the IAM.

=== 3.6 HTTP client

* `cookiejar.New(nil)` for browser journeys.
* `CheckRedirect` to stop before the redirection when testing the URL.
* `CountingTransport` to count calls per host/path.

== 6. Test details

=== AC-AUTH-01 — Google login

`TestAC_AUTH_01_GoogleLoginCreatesSession`

Steps:

. Start the fake Google, the test IAM, Gate One with the `mycompany` provider.
. `GET /` on `app.mycompany.test` without a cookie.
. Follow the redirection to the IAM then to Google.
. Google auto-consent, IAM callback, Gate One callback.
. Check the session cookie, `roles`, `tenant`, `sid`.

Assertions:

* `200` on the protected page;
* `cladone_mycompany_session` cookie present, `HttpOnly`, `Secure`, `SameSite=Lax`;
* claims `tenant=mycompany`, expected `roles`, non-empty `sid`;
* no Google cookie on the Gate One domain;
* the IAM has never transmitted the Google token to Gate One.

Subtests:

* `google_consent_ok`;
* `workspace_hd_required`;
* `email_unverified_rejected`;
* `wrong_nonce_rejected`;
* `wrong_state_rejected`;
* `pkce_required`.

=== AC-AUTH-02 — Cross-tenant

`TestAC_AUTH_02_CrossTenantTokenRejected`

Table:

[cols="2,2,2"]
|===
| Token | Route | Expected

| `iss=mycompany`, `aud=mycompany` | `contoso` | `401`
| `iss=contoso`, `aud=contoso` | `mycompany` | `401`
| `iss=mycompany`, `aud=contoso` | `contoso` | `401`
| `tenant=mycompany` in claims, `iss=contoso` | `mycompany` | `401`
| valid mycompany token | `mycompany` | `200`
|===

The test also verifies that the identity cache is not shared: two providers
of the same `oidc` type must not have the same cache key.

=== AC-AUTH-03 — Local validation

`TestAC_AUTH_03_MCPValidationUsesJWKSOnly`

* First MCP call: a JWKS fetch is allowed.
* Subsequent calls with the same `kid`: `CountingTransport` must show **zero**
  calls to the IAM.
* The IAM is then stopped; the still-valid token must continue to pass.
* A token with an unknown `kid` must trigger a fetch; if the IAM is down,
  `502`.

=== AC-AUTH-04 — Key rotation

`TestAC_AUTH_04_KeyRotationKeepsSessions`

* Issue a token with `kid=mycompany-2026-01`.
* Publish `mycompany-2026-02` in JWKS.
* Issue a new token with `mycompany-2026-02`.
* Verify that the old and the new token are accepted during the overlap.
* Advance the clock beyond the expiration of the old token.
* Remove `mycompany-2026-01` from the JWKS.
* Verify that no Gate One session is logged out by the rotation.

Subtests:

* `old_token_valid_during_overlap`;
* `new_kid_triggers_refresh`;
* `old_key_retired_after_ttl`;
* `rotation_does_not_clear_session_cookie`.

=== AC-AUTH-05 — Back-channel logout

`TestAC_AUTH_05_BackchannelLogoutRevokesSession`

* Log in, retrieve `sid`.
* IAM sends a signed logout token to `/backchannel-logout`.
* Check the revocation store.
* Next request with the cookie: `401`.
* The identity cache is invalidated.
* A replayed logout token is idempotent.
* A badly signed logout token is refused without revocation.

=== AC-AUTH-06 — Degraded mode per tenant

`TestAC_AUTH_06_BrokerDownDegradesOnlyTenant`

Scenario:

. Two tenants `mycompany` and `contoso`, two IAMs.
. Log in on both.
. Stop the `mycompany` IAM.
. Request with the `mycompany` session: `200` (local validation).
. New `mycompany` login: `502`.
. `mycompany` MCP with the `kid` in cache: `200`.
. `mycompany` MCP with an unknown `kid`: `502`.
. `contoso` routes: `200`.
. `/healthz`: `200`.
. `/readyz`: `200` because `contoso` still serves.
. `/__gate-one/health/providers`: `mycompany=degraded`, `contoso=ready`.

=== AC-AUTH-09 — `IdentityAdapter` conformance

`TestAC_AUTH_09_IdentityAdapterConformance`

The `pkg/identityadapter/conformance.Run(t, adapter)` suite is run against:

* the built-in OIDC adapter + fake Google;
* the fake `IdentityAdapter`;
* later LDAP + fake LDAP;
* the HTTP client (`httpbinding`);
* the gRPC client (V2).

Assertions:

* `Start` returns a valid `Step`;
* `Continue` returns `Result` or a classified error;
* `State` is opaque, signed, single-use, with a TTL;
* `Assertion` contains only facts;
* `Enrich` absent = skip;
* `Health` classifies timeout/500/malformed;
* no `roles`/`tenant`/`aud` decision in the adapter.

=== AC-AUTH-10 — HTTP binding (parity with in-process)

`TestAC_AUTH_10_HTTPBindingParity`

The same conformance suite is run twice:

* in-process adapter;
* HTTP/JSON adapter (`pkg/identityadapter/httpbinding`).

The results are compared: same `Step.Kind`, same errors, same assertions
(normalisation of random fields such as `State`).

=== AC-AUTH-11 — Optional enrichment

`TestAC_AUTH_11_EnrichmentOptional`

* Adapter without the `Enrichment` capability: the IAM does not call it.
* Adapter with the capability: the enriched claims are merged.
* Enrichment failure: `fail_closed` policy (default) → login refused;
  `fail_open` → login accepted without enrichment.
* The adapter cannot override `tenant`/`roles` decided by the IAM.

`TestAC_AUTH_14_InvalidTokenVsUnavailable`

=== AC-AUTH-15 — Degraded startup/reload

`TestAC_AUTH_15_DegradedStartupAndReload`

* Startup with `mycompany` down, `contoso` up: the process starts; `mycompany` `degraded`,
  `contoso` `ready`; `contoso` routes `200`.
* Reload with `mycompany` down: new generation; `mycompany` `degraded`; `contoso`
  updated.
* Reload with invalid config: refused; previous generation active.
* Reload with a provider that comes back: `mycompany` returns to `ready` after the health check.
* Drain: in-flight requests on the previous generation complete.

=== AC-AUTH-16 — Plugin V2

`TestAC_AUTH_16_PluginManifestV2`

* valid manifest + valid signature + valid digest → loaded;
* unknown key → refused;
* invalid signature → refused;
* digest mismatch → refused;
* incompatible `hostAPI` → refused;
* missing dependency → refused;
* revoked digest → refused;
* `auth` capability in a route plugin → refused;
* downgrade to a vulnerable version → refused.

=== AC-AUTH-17 — No secret leak

`TestAC_AUTH_17_NoSecretLeak`

* Capture the logs and the error bodies.
* Verify the absence of token, code, password, private key, client secret.
* Verify that `502` errors do not contain the full internal URL if it
  contains credentials.
* Verify that `-check` does not serialise secrets.

== 9. Staging and drills

=== 9.1 Real Google

* Dedicated Google test tenant.
* Journeys: login, consent, refusal, revocation, logout.
* Check `hd`, `email_verified`, groups.
* Nightly or manual before release.

=== 9.2 Browsers

* Chrome, Firefox, Safari.
* `SameSite` cookies, domains, ITP.
* Logout, refresh, expiration.
* Playwright in staging.

=== 9.3 Key rotation

* Publish the new key.
* Wait for the JWKS TTL.
* Sign with the new one.
* Verify the absence of logout.
* Remove the old one after expiration.
* Runbook and rollback.

=== 9.4 Revocation

* Back-channel logout.
* Check the Gate One session.
* Check idempotence.
* Check the IAM down case.

=== 9.5 IAM failure

* Stop a tenant's IAM.
* Check the existing sessions.
* Check the new logins.
* Check the other tenants.
* Check `/healthz`, `/readyz`, logs, alerts.

=== 9.6 Restore

* Restore SQLite and keys.
* Verify that existing sessions/tokens remain valid or are revoked
  according to the policy.
* Verify that an invalid `storeID` invalidates the cookies if the database is lost.

== 10. Non-regression policy

* Each criterion has an `AC-AUTH-NN` ID present in the test name.
* Each fixed bug adds a test that fails before the fix.
* Contract tests are versioned with `apiVersion`.
* Golden files cover discovery, JWKS, resolved config.
* Optional mutation testing on `internal/authn` and `internal/iam`.
* Any change to `IdentityAdapter` updates the conformance suite.
* Any change to an HTTP status updates matrix 2.3.
* Test secrets are marked `TEST ONLY` and scanned by `gitleaks`.

=== 12.3 HTTP statuses

[cols="2,1,2"]
|===
| Case | Status | Login offered

| missing/invalid/expired token | `401` | yes (navigation)
| insufficient scope | `403` | no
| identity refused | `403` | no
| provider/JWKS/store unavailable | `502` | no
| invalid config | — | startup/reload refused
| rate limit | `429` | no
|===

=== 12.4 Glossary

* **Provider**: Gate One configuration of an OIDC/JWT issuer.
* **IAM**: service that federates the IdPs and re-issues JWTs.
* **IdentityAdapter**: the IAM's internal contract for an IdP protocol.
* **Tenant**: isolation domain (issuer, key, audience, cookies, store).
* **Fail-fast per tenant**: the failure of one provider degrades its routes, not the
  other tenants.
* **Invalid token**: the client can fix it (`401`).
* **Provider unavailable**: Gate One cannot verify (`502`).

=== 13.2 Known limitations

* The IAM uses Redis when `redis` is configured; otherwise the in-memory
  store remains the test/dev default. In multi-instance production,
  Redis is required.
* The gRPC binding is not yet implemented; the contract and the HTTP
  binding are ready.
* The staging tests (real Google, browsers, load, chaos) are not
  automated in this repository.
* The degraded mode covers startup, reload and runtime failure.
* The full Gate One <-> IAM browser E2E (domain cookie,
  real redirections) is not automated in this repository: the building
  blocks are tested separately (IAM with fake Google, OIDC wiring, JWT/JWKS).
  Staging with real Google remains the final validation.
