= Cladone G.O. Gate One — embedded IAM (`cladone-auth`)
:toc:
:toclevels: 2

== 1. Role

The IAM is a **multi-tenant OIDC/JWT issuer**:

* it federates login to Google (V1);
* it enforces the local policy (tenant, roles, audiences);
* it re-issues its own Ed25519-signed JWTs;
* Gate One only trusts the IAM, never Google.

Gate One loads **no provider plugin**. It only knows
`type: "oidc"` (browser/MCP) and `type: "jwt"` (API Bearer).

== 2. Flow

== 2.1 Browser

----
Browser
  -> Gate One (mycompany route, no session)
  -> IAM /t/mycompany/authorize
  -> Google
  -> IAM /t/mycompany/callback
  -> Gate One /auth/callback
  -> Gate One session
----

== 2.2 Shared session and global logout

The IAM sets a **host-only** session cookie on its own host,
with `Path=/t/{tenant}`. All applications in the same browser
that go through this tenant reuse the same OIDC `sid`.

Consequence:

* a logout from any Gate One app revokes the user's `sid` **and
  `sub`**; all their existing sessions, across all
  browsers/devices, are refused on the next request;
* `/t/{tenant}/logout` also revokes `sid`/`sub` (cookie or
  `id_token_hint`), deletes the IAM session and clears the cookie;
* `sub` revocation carries a timestamp: sessions/tokens issued
  **before** the logout are refused, but a new login after the logout
  is allowed (no user lockout);
* refresh tokens and authorization codes issued before the logout are
  refused at exchange;
* Gate One derives its default `revocationTtlSeconds` from the
  discovery field `cladone_refresh_token_ttl_seconds` published by the IAM:
  revocation therefore covers refresh tokens without manual configuration.

The cookie is useless to applications: it is only sent to the IAM.
The shared `sid` is used for per-browser logout; the `sub` guarantees
global user logout.

== 2.3 Machine / MCP

----
M2M client
  -> IAM /t/mycompany/token (client_credentials)
  -> access token JWT (aud = MCP resource)
  -> Gate One Authorization: Bearer
  -> local JWKS validation
----

----

== 4. Rights, mappings and users

The IAM has two sources of rights:

* the IdP claim **mappings**, recomputed on each federated login;
* the **grants** stored on the IAM user, for both local
  and federated accounts.

Effective rights are the union:

----
tenant defaults
+ adminEmails
+ claim mappings (federated)
+ user roles/scopes/claims
----

=== Mappings

[source,json]
----
"mappings": [
  {
    "claim": "groups",
    "values": ["admins"],
    "roles": ["admin"]
  },
  {
    "claim": "realm_access.roles",
    "values": ["offline_access"],
    "roles": ["user"]
  },
  {
    "claim": "department",
    "scopes": ["read:things"],
    "claims": { "department": "support" }
  }
]
----

`claim` is a dotted path into the token claims. Empty `values` =
presence of the claim. Reserved claims (`sub`, `iss`, `aud`, `roles`,
`scope`, etc.) cannot be overridden. The legacy `groupRoles` block
remains supported for the single claim `groups`.

=== Local and federated users

A user has **a single external link** `(issuer, subject)` for
federated accounts. On the first federated login, the IAM creates a
JIT user without rights; the admin can then assign roles/scopes/claims to it.
A local account has a password and the same rights fields.

The IAM never recreates the IdP account. It only stores the
authorization profile and its identity link.

The CLI works on the same configuration and the same Redis store:

[source,bash]
----
# compte local
cladone-auth user create -config cladone-auth.json -tenant mycompany \
  -kind local -email alice@mycompany.example.com \
  -password 'mot-de-passe-long' -roles support \
  -scopes read:things -claims '{"department":"support"}'

# federated account (JIT or pre-provisioned)
cladone-auth user create -config cladone-auth.json -tenant mycompany \
  -kind federated -issuer https://accounts.google.com -sub 'google-sub-1' \
  -email alice@mycompany.example.com -roles support

# lister / inspecter
cladone-auth user list -config cladone-auth.json -tenant mycompany
cladone-auth user show -config cladone-auth.json -tenant mycompany \
  -issuer https://accounts.google.com -sub 'google-sub-1'

# replace the grants (federated user: lookup by identity)
cladone-auth user set -config cladone-auth.json -tenant mycompany \
  -issuer https://accounts.google.com -sub 'google-sub-1' \
  -roles support,auditor -scopes read:things \
  -claims '{"department":"support"}'

# relink a federated user to a new subject (Auth0 change)
cladone-auth user set -config cladone-auth.json -tenant mycompany \
  -id <user-id> -new-issuer https://tenant.eu.auth0.com/ -new-sub 'auth0|...'
----

`user set` replaces the provided role/scope lists and claims object.
Changes take effect at the next login; to invalidate them
immediately, use `cladone-auth revoke` on the relevant `sub`/`sid`.

== 6. Policy

* `tenant`: tenant identifier, in the ID token and the access token.
* `roles`: `defaultRoles` + `adminEmails` + `groupRoles`.
* `aud`: resource audience for access tokens; `clientId`
  for the ID token.
* `sid`: session identifier, used by revocation.
* `allowedDomains`: restricts `hd` / Google email domain.
* `email_verified`: refused if explicitly `false`.

The IAM does not decide access to Gate One routes. It authenticates and
asserts an identity; Gate One applies `auth.when` / `auth.identity`.

== 7. Degraded mode

Gate One builds each provider independently:

* a provider whose discovery fails is `degraded`;
* its routes respond `502 authentication_unavailable`;
* the other tenants continue;
* local sessions already issued remain valid;
* an invalid token remains `401`, a JWKS failure becomes `502`.

The IAM must be supervised per tenant: `/health` and the logs.

== 8. Redis, revocation and V1 limits

The IAM uses Redis if the `redis` block is present. In multi-instance
production, Redis is required: flows, codes and refresh tokens must
survive restarts and be shared. Without a `redis` block, the IAM
uses an in-memory store (tests/dev).

The IAM writes `sid`/`sub` revocations into the `authPrefix` space;
Gate One reads them with the same prefix. Revocation is
therefore visible on the next request on all instances. If Redis
is unavailable, Gate One fails closed with `502` on authenticated
routes.

For an HA Redis instance, the `redis` block accepts Sentinel mode,
with sentinel authentication and TLS:

[source,json]
----
"redis": {
  "masterName": "authmaster",
  "sentinelAddrs": ["redis-sentinel-1:26379", "redis-sentinel-2:26379"],
  "sentinelUsername": "sentinel-user",
  "sentinelPasswordEnv": "REDIS_SENTINEL_PASSWORD",
  "username": "app",
  "passwordEnv": "REDIS_PASSWORD",
  "tls": true,
  "tlsCaFile": "/etc/cladone-auth/redis-ca.pem",
  "prefix": "cladone:iam:v1:",
  "authPrefix": "cladone:auth:v1:"
}
----

`tls` covers connections to the sentinels and the discovered master. In
URL mode, use `rediss://`; the `tls*` and `sentinelUsername` fields
are refused with a URL.

Other V1 limits:

* Google only as upstream IdP; Entra/Authentik/Keycloak are generic
  OIDC clients to be added.
* Refresh token encryption at rest not implemented (the Redis keys
  must be protected by ACL/TLS).
* No SAML/LDAP (V1.1/V2); they will go through `IdentityAdapter`.
* No gRPC for adapter plugins; the HTTP/JSON binding is
  implemented (`pkg/identityadapter/httpbinding`).
* No mTLS/API key on the Gate One side: the IAM authenticates the client and
  issues a JWT (V1.1).

== 9. Launch and rotation

[source,bash]
----
make build-auth
./bin/cladone-auth -config testdata/auth/embedded-iam.example.json -addr :8081

# New key: append it at the END of keyFiles, reload, then remove
# the old one after the tokens signed with it expire.
./bin/cladone-auth keygen -out keys/mycompany-2026.key

# Immediate revocation of a session or a user (Redis required).
# Without -ttl, the duration is the tenant refresh token (never
# shorter than the session): a shorter revocation would let a
# still-valid refresh token recreate a session after logout.
./bin/cladone-auth revoke -config cladone-auth.json \
  -tenant mycompany -sid <sid>
----

`keyFiles` is ordered from oldest to newest: the last key
signs, all published keys remain in JWKS during the
overlap. `keyFile` is still accepted for a single key; the two
are mutually exclusive.
