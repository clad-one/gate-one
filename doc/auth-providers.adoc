= Authentication providers

Gate One never implements an identity provider for production. It
delegates request verification to a provider. Four implementations
share one contract:

[options="header",cols="1,2,2"]
|===
| type | What it is | External dependency

| `dev` | Embedded development IdP: dedicated `login.<domain>` host,
real alice/bob form, signed session cookie, MCP dev tokens. Loopback
only. | none
| `http-bridge` | Any service speaking the Gate One HTTP bridge
contract (`GET /auth`, `/auth/mcp`, `/login`, `/logout`,
`/auth/popup-done`, `/health`). auth-bridge is the reference
implementation; a non-conforming service needs an adapter. | auth-bridge,
or a custom bridge
| `oidc` | Native OpenID Connect Relying Party: discovery, code + PKCE,
state/nonce, JWKS, signed session, RP-initiated logout, local MCP
bearer verification. | an OIDC IdP
| `jwt` | Stateless JWKS bearer verifier for API/MCP routes; no login
page, no session cookie. | a JWT issuer with JWKS
|===

The legacy spelling `http` is accepted as a deprecated alias of
`http-bridge`; new configurations should use `http-bridge`. The bridge
contract is documented in the product docs (`HTTP bridge contract`).

For multi-tenant hosting, use the plural `authProviders` block and bind
each route with `auth.provider`. Only `oidc` and `jwt` are allowed in
this form; `http` (auth-bridge) and `dev` remain legacy single-provider
modes. A provider that is unreachable at startup is degraded per tenant:
its routes answer 502, the other tenants continue. See
`doc/auth-broker.adoc` and `doc/auth-test-plan.adoc`.

Absent `authProvider` keeps the legacy `oidc` + auth-bridge behaviour:
existing configurations need no edit.

For multi-instance or immediate revocation, set the OIDC revocation
store to Redis:

[source,json]
----
"authProvider": {
  "type": "oidc",
  "...": "...",
  "sessionKeyEnv": "OIDC_SESSION_KEY",
  "sessionStore": {
    "type": "redis",
    "url": "redis://redis:6379/0",
    "passwordEnv": "REDIS_PASSWORD",
    "prefix": "cladone:auth:v1:"
  }
}
----

`sessionKeyEnv` is mandatory for OIDC+Redis: every instance must sign
the same session cookie. bbolt remains valid for a single instance.
Redis is checked on every authenticated request; if it is unavailable,
authenticated routes fail closed with `502 authentication_unavailable`
(public routes are unaffected).

For a highly available Redis, use Sentinel mode. The Sentinels may
require their own credentials (separate from the Redis ACL user) and
TLS:

[source,json]
----
"sessionStore": {
  "type": "redis",
  "masterName": "authmaster",
  "sentinelAddrs": ["redis-sentinel-1:26379", "redis-sentinel-2:26379"],
  "sentinelUsername": "sentinel-user",
  "sentinelPasswordEnv": "REDIS_SENTINEL_PASSWORD",
  "username": "app",
  "passwordEnv": "REDIS_PASSWORD",
  "tls": true,
  "tlsCaFile": "/etc/gate-one/redis-ca.pem",
  "tlsServerName": "redis.internal",
  "prefix": "cladone:auth:v1:"
}
----

`tls` applies to both the Sentinel connections and the discovered
master/replica. In URL mode, use a `rediss://` URL instead; `tls`,
`tlsCaFile`, `tlsServerName` and `sentinelUsername` are rejected with a
URL. `tlsCaFile` is optional (system roots by default) and is checked at
startup. `tlsServerName` is useful when the Sentinels are addressed by
IP.

`revocationTtlSeconds` defaults to the issuer's advertised
`cladone_refresh_token_ttl_seconds` (the broker exposes its refresh-token
lifetime), otherwise 30 days, and is never shorter than the session TTL.
Set it explicitly only if the issuer does not advertise the value; a
shorter value would let a refresh token outlive a global logout.

When the value is absent from both the config and the discovery, Gate One
logs a startup warning with typical places to find the IdP refresh-token
lifetime (Keycloak Tokens, Entra token lifetime policy, Auth0/Okta
settings). `-check` performs the same best-effort discovery probe; an
unreachable issuer is reported as a warning, not a config failure.

== Quickstart

Public site (no authentication at all):

[source,bash]
----
gate-one init --static --host app.localhost --backend http://127.0.0.1:8080
gate-one -config api-routes.json
----

Development SSO (embedded IdP, no external service):

[source,bash]
----
gate-one init --host app.demo.localhost --backend http://127.0.0.1:8080
gate-one -config api-routes.json
# login: alice/alice (user), bob/bob (admin)
----

Native OIDC (production):

[source,bash]
----
export OIDC_CLIENT_SECRET=...      # never put it in the JSON
gate-one init --oidc --host app.example.com \
  --backend http://127.0.0.1:8080 \
  --issuer https://auth.example.com/realms/mycompany \
  --client-id gate-one
gate-one -config api-routes.json
----

The generated configuration:

[source,json]
----
{
  "authProvider": {
    "type": "oidc",
    "issuer": "https://auth.example.com/realms/mycompany",
    "clientId": "gate-one",
    "clientSecretEnv": "OIDC_CLIENT_SECRET",
    "loginBaseUrl": "https://login.example.com",
    "cookieDomain": "example.com",
    "sessionStore": {"type": "bolt", "path": "./gate-one-state.db"},
    "sessionTtlSeconds": 3600,
    "backchannelLogout": true
  },
  "routes": [{
    "host": "app.example.com", "path": "/*", "frontend": true,
    "backend": "http://127.0.0.1:8080", "auth": {}
  }]
}
----

== OIDC IdP registration

Register a confidential (or public + PKCE) client at the IdP:

* redirect URI: `https://login.example.com/auth/callback`
* post-logout redirect URI: `https://app.example.com/` (and every
  other public host that uses the badge/logout)
* back-channel logout URI: `https://login.example.com/backchannel-logout`
  (optional; Gate One auto-enables the endpoint when the IdP discovery
  advertises `backchannel_logout_supported`)
* scopes: `openid profile email` (add `offline_access` only if a later
  refresh-token lot needs it)

`login.example.com` must resolve to Gate One and be covered by the TLS
certificate; Gate One serves `/login`, `/auth/callback`, `/logout`,
`/backchannel-logout`, `/auth/popup-done` and `/health` on that host
before any application route. The session cookie is set on `cookieDomain`
(e.g.
`example.com`), so every `*.example.com` app shares the session.

If the client is public (no secret), omit `clientSecretEnv`: PKCE S256
is used either way. A missing environment variable for a declared
`clientSecretEnv` refuses startup, like the token-broker secret.

The IdP **account console** has no standard OIDC URL: set it explicitly
on the connector (the badge displays it when configured):

[source,json]
----
"authProvider": {
  "type": "oidc",
  "...": "...",
  "links": {
    "account": {
      "label": "Account",
      "url": "https://auth.example.com/realms/example/account/"
    }
  }
}
----

The token-broker connections page is a separate link, owned by the
broker (`tokenBroker.links.services`), and only shown when an exposed
route delegates. See `docs/api-routes.adoc` (userBadge links).

== Claim mapping

Defaults, suitable for Keycloak:

* roles: `realm_access.roles`, `resource_access.<clientId>.roles`,
  `groups`
* scopes: `scope` (space-separated); `scp` (string or array) is also
  read for Entra-style tokens
* identity: `sub` (user id), `preferred_username` (username), `email`

Override the role paths with `roleClaims` and the scopes claim with
`scopesClaim`. A dot path traverses nested objects: use one path per
source (a client id containing a dot is not addressable by this
minimal syntax; list the relevant roles under `groups` or a custom
claim instead).

== MCP

Gate One becomes the resource server: it validates the Bearer JWT
locally against the IdP JWKS, checks the required scope, and never
calls auth-bridge. The IdP must issue an access token whose `scope`
contains the MCP scope (default `mcp-tools`) and whose audience matches
what the MCP client requested.

By default only the scope is enforced, because Keycloak does not add a
resource audience without an audience mapper. Set `mcpAudience: "auto"`
to require the endpoint's own protected-resource identifier in `aud`
(recommended when the mapper exists), or a literal `aud` value. Opaque
access tokens are not accepted by the native provider; use `type: http-bridge`
with auth-bridge when the IdP only issues opaque tokens.

== Sessions, revocation and logout

The RP session is a signed HttpOnly cookie (HMAC) set on
`cookieDomain`; the default lifetime is 1h (`sessionTtlSeconds`). It is
independent of the short ID-token expiry: otherwise a 5-minute Keycloak
token would force a full re-login every five minutes. A short TTL
bounds revocation when no shared store is used.

For Keycloak, do **not** request `offline_access` for the browser RP
session: it creates an *offline* session, and backchannel logout for
offline tokens depends on the client's
`backchannel.logout.revoke.offline.tokens` attribute (false by
default). A confidential client still receives a refresh token without
`offline_access`; the online session is the one Keycloak logs out and
notifies through backchannel.

Keycloak prefers **front-channel** logout when the client's
`frontchannelLogout` flag is true, even if `backchannel.logout.url` is
set. To use backchannel, set `frontchannelLogout: false` on the client
and keep the backchannel URL; the front-channel URL is then ignored.

Revocation state lives in a **bbolt** file (`sessionStore.type: bolt`,
default `./gate-one-state.db` relative to the config file):

* `/backchannel-logout` validates the OIDC logout token (signature,
  `iss`, `aud`, `iat`, `events`, `sid`/`sub`, replay `jti`) and records
  the revocation synchronously;
* `sid` revokes one session; `sub` revokes every session of the user
  issued **before** the revocation timestamp (a new login after logout
  remains possible);
* the revocation is checked **before** the gateway identity cache, so a
  cached identity cannot survive a logout;
* entries expire after `revocationTtlSeconds`, default: issuer's
  advertised refresh-token TTL, else 30 days, never shorter than the
  session TTL.

bbolt is single-writer: a second Gate One instance on the same file is
refused. For HA and immediate cross-instance revocation, use
`sessionStore.type: redis`; it also requires `sessionKeyEnv` so all
instances share the cookie key.
Losing/recreating the state file changes the store identity embedded in
the cookie, so old sessions are rejected instead of being reactivated.
`sessionKeyEnv` is optional for a single instance (the key is persisted
in bbolt); set it when multiple instances must accept the same cookie.

Logout clears the cookie, revokes the session `sid` locally (a copied
cookie cannot be replayed), and redirects to the IdP
`end_session_endpoint` with `id_token_hint` and
`post_logout_redirect_uri` when the IdP advertises one. The ID token is
kept only for that hint. In native mode the refresh token is not stored
by Gate One; with `legacyTokenCookies` (migration, see below) the
access/refresh/id tokens are mirrored in cookies for auth-bridge, the
same custody model auth-bridge has always used.

== Sharing the login host with auth-bridge (migration)

Native OIDC can share `login.<domain>` with auth-bridge while the
token-broker proxy routes are still served by auth-bridge:

* Traefik routes `/connections`, `/connect/*`, `/oauth/*`,
  `/frontchannel-logout`, `/auth` and `/auth/mcp` to auth-bridge;
* every other path (`/login`, `/auth/callback`, `/logout`,
  `/backchannel-logout`, `/auth/popup-done`, `/health`) goes to Gate One;
* set `legacyTokenCookies: true`: Gate One also writes the
  `access_token` / `refresh_token` / `id_token` cookies on the shared
  cookie domain, so auth-bridge's `/connections` and `/connect` resolve
  the same session without a second login;
* set `frontchannelLogout: false` on the `cladone-login` client (keep
  its backchannel URL): Keycloak prefers frontchannel when this flag is
  true and never calls `/backchannel-logout`;
* set `backchannelForwardUrl: "http://auth-bridge:3000/backchannel-logout"`:
  the native endpoint forwards each valid logout token to auth-bridge,
  keeping its persistent `sid` list in sync for `/auth` (forwardAuth)
  and `/connections`;
* back-channel logout goes to Gate One (`/backchannel-logout`) and
  revokes the native session immediately. The forward is best effort:
  a failure never fails Keycloak's request.

This is a migration setup. Once the token-broker proxy routes are
served by Gate One (or no longer needed), set `legacyTokenCookies` to
false and give the native provider a dedicated login host.

== auth-bridge remains an option

Use `type: "http-bridge"` to keep auth-bridge (including in front of
Keycloak):

[source,json]
----
{
  "authProvider": {
    "type": "http-bridge",
    "baseUrl": "http://auth-bridge:3000",
    "loginUrl": "https://login.example.com/login",
    "issuer": "https://auth.example.com/realms/example"
  }
}
----

This is also the adapter for non-OIDC identity (SAML gateways, LDAP
front-ends, GitHub OAuth2): the service must expose the Gate One
contract. `verifyUrl`, `mcpVerifyUrl`, `healthUrl` and `headers` can be
overridden, but that only adapts the verification call: `/login`,
`/logout`, `/auth/mcp` and `/auth/popup-done` remain the contract.

Examples: `examples/http.api-routes.json` (auth-bridge) and
`examples/oidc.api-routes.json` (native).

== Migrating the legacy `oidc` block

The legacy block:

[source,json]
----
"oidc": {
  "loginUrl": "https://login.example.com/login",
  "issuer": "https://auth.example.com/realms/example"
}
----

is **behaviorally identical** to:

[source,json]
----
"authProvider": {
  "type": "http-bridge",
  "loginUrl": "https://login.example.com/login",
  "issuer": "https://auth.example.com/realms/example"
}
----

`baseUrl` is optional (default `http://auth-bridge:3000`). This shape
migration changes neither the session nor the auth path: `-check`, then
`SIGHUP`. Keep it as the production baseline as long as auth-bridge is
needed for other consumers (forward-auth, token-broker connections).

Switching that block to `type: "oidc"` is **not** a shape migration: it
moves the login and session to Gate One. It requires the native OIDC
prerequisites (shared session key, per-endpoint MCP audience, refresh
and/or `prompt=none`, backchannel logout, and a decision for
`/connections`). Plan a staging login host and a dedicated Keycloak
client; do not cut production over before that parity exists.

== Authelia, Authentik, other IdPs

* **Authentik**: an OIDC provider — use `type: "oidc"` directly.
* **Keycloak**: `type: "oidc"` directly, or `type: "http-bridge"` with
  auth-bridge when its hardened session/refresh/popup flow is wanted.
* **Authelia**: a forward-auth portal, *not* an implementation of the
  Gate One contract. It needs an adapter for `/auth`, `/auth/mcp` and
  `/auth/popup-done`; overriding `verifyUrl`/`headers` is not enough.
* **SAML / LDAP / GitHub OAuth2**: `type: "http-bridge"` plus an adapter
  (auth-bridge or custom).

== Troubleshooting

[source,bash]
----
gate-one -config api-routes.json -check   # grammar + best-effort OIDC TTL warning
gate-one doctor -config api-routes.json   # discovery + provider health
----

An unreachable provider answers `502 authentication_unavailable`
(readable HTML for a navigation, JSON for a fetch) — never a login
redirect, which would loop. A public frontend route needs no `oidc`
block at all. The embedded `dev` provider refuses a non-loopback bind;
`--dev-allow-remote` is reserved for a demo.
