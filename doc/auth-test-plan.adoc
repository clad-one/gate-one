= Cladone G.O. Gate One — Plan de test authentification
:toc:
:toclevels: 3
:icons: font

== 1. Objet et périmètre

Ce plan couvre l'authentification de Gate One et du broker OIDC :

* Gate One ne connaît que **OIDC/JWT** ; il ne charge aucun plugin de provider.
* Le broker est un **émetteur OIDC/JWT** : il fédère Google, applique la politique
  (rôles, tenant, audiences), puis ré-émet ses propres JWT signés.
* Le contrat interne du broker est `IdentityAdapter` : un seul contrat, plusieurs
  implémentations par protocole (OIDC, puis LDAP/mTLS/API key), un seul mécanisme
  de chargement pour les plugins.
* Le mode dégradé est **fail-fast par tenant uniquement** : la panne d'un provider
  ne doit jamais bloquer les autres tenants.
* Les erreurs **token invalide** et **provider/réseau indisponible** sont
  distinctes, avec des statuts HTTP différents.

Hors périmètre V1 :

* SAML et LDAP (V1.1/V2) ;
* PASETO ;
* appels réels à Google en CI (faux Google + staging) ;
* mTLS/API key côté Gate One (V1.1, via le broker).

== 2. Décisions de comportement

=== 2.1 Fail-fast par tenant

Le chargement de configuration reste **globalement strict** : une erreur de
grammaire, un provider inconnu, un ID dupliqué ou une route incohérente refusent
le chargement ou le reload. En revanche, la **disponibilité** d'un provider est
isolée par tenant.

[cols="1,3,3,2"]
|===
| Situation | Gate One | Routes du tenant concerné | Autres tenants

| Config invalide
| `core.Load` échoue ; au reload, l'ancienne génération reste active
| Aucun changement
| Aucun changement

| Provider down au démarrage
| Le process démarre ; le provider est marqué `degraded`
| Les opérations qui nécessitent le provider répondent `502 authentication_unavailable`
| Démarrent normalement

| Provider down à l'exécution
| Le provider passe `degraded` ; health et logs exposent l'état
| Sessions locales encore valides : `200` ; nouveau login : `502` ; MCP avec clé JWKS en cache : `200` ; `kid` inconnu : `502`
| Inchangés

| Reload avec provider down
| La nouvelle génération est construite ; le provider fautif est `degraded`
| Routes mises à jour, provider fautif en `502`
| Mises à jour normalement

| Reload avec config invalide
| Reload refusé ; l'ancienne génération reste active
| Aucun changement
| Aucun changement

| Tous les providers down
| Le process reste vivant ; `/readyz` peut passer `503` si aucune route publique ne peut servir
| `502` sur les routes authentifiées
| Routes publiques éventuelles inchangées
|===

Règles :

* Un provider en `degraded` ne signifie **pas** que toutes ses routes répondent
  `502`. Les sessions déjà émises restent valides localement jusqu'à leur
  expiration ; seules les opérations qui nécessitent un appel au provider
  échouent en `502`.
* Le démarrage ne doit pas être bloqué par un provider indisponible, sauf si la
  configuration elle-même est invalide.
* Au reload, un provider dont la configuration a changé et dont la construction
  échoue est `degraded` ; l'ancien provider n'est pas réutilisé pour une
  configuration différente.
* Les instances de l'ancienne génération sont fermées après drainage.

Health :

* `/healthz` : liveness, `200` tant que le process répond.
* `/readyz` : `200` si Gate One peut servir au moins une route ; `503` si aucun
  provider n'est prêt et qu'aucune route publique n'existe.
* `/__gate-one/health/providers` (admin) : état JSON par provider.
* `gate-one doctor` : un statut par provider, sans démarrer le serveur.

=== 2.2 Classification des erreurs

[cols="2,2,1,3"]
|===
| Condition | Erreur interne | HTTP | Réponse

| Token absent, malformé, signature invalide, expiré, `nbf` futur, mauvais `iss`/`aud`
| `ErrUnauthenticated`
| `401`
| JSON ou challenge MCP ; redirection login pour navigation frontend

| Scope MCP insuffisant
| `ErrInsufficientScope`
| `403`
| `WWW-Authenticate: Bearer error="insufficient_scope"`

| Conditions d'identité (`roles`, `scopes`, `claims`, `user`) non satisfaites
| `ErrPolicyDenied`
| `403`
| Page/JSON `forbidden` ; pas de redirection login automatique ; action « se déconnecter et changer de compte » sur la page (provider interactif)

| JWKS inaccessible, timeout, TLS, réponse malformée
| `ErrProviderUnavailable`
| `502`
| `authentication_unavailable`, jamais de redirection login

| Découverte OIDC inaccessible au login
| `ErrProviderUnavailable`
| `502`
| `authentication_unavailable`, jamais de redirection login

| Store de révocation en erreur
| `ErrProviderUnavailable`
| `502`
| Fail-closed ; jamais `401`

| Provider inconnu, config invalide, ID dupliqué
| erreur de chargement
| — | Démarrage/reload refusé

| Route publique + `auth.provider` | erreur de chargement | — | Démarrage/reload refusé

| Rate limit / quota
| `ErrRateLimited`
| `429`
| Réponse existante du proxy
|===

Règles :

* `401` = le client peut corriger sa requête (token absent/invalide/expiré).
* `403` = le client est authentifié mais n'a pas le droit.
* `502` = Gate One ne peut pas vérifier ; le client ne peut pas corriger.
* Un `502` ne doit **jamais** proposer un login : boucle garantie.
* Un `401` MCP porte `WWW-Authenticate` ; un `502` MCP n'en porte pas.

=== 2.4 Impacts d'implémentation requis par ces tests

* `providerRegistry` avec états `starting`, `ready`, `degraded`, `closed`.
  `proxy.New` construit chaque provider indépendamment ; un échec de découverte
  ne retourne pas d'erreur globale, il marque le provider `degraded`.
* `Gateway.ProviderStatus()` et `ProviderHealth()` pour `/healthz`,
  `/readyz`, `/__gate-one/health/providers` et `doctor`.
* `classifyingKeySet` autour de `go-oidc` : distinguer
  `ErrUnauthenticated` (signature, claims, token) de
  `ErrProviderUnavailable` (JWKS HTTP, timeout, TLS, réponse malformée).
  Un `kid` inconnu avec refresh JWKS réussi et token invalide reste `401` ;
  un refresh impossible devient `502`.
* `ErrProviderUnavailable` mappé en `502 authentication_unavailable` dans le
  proxy et le handler MCP ; `WWW-Authenticate` uniquement sur `401`.
* `authCache` clé par `provider.ID()` et non `provider.Name()`.
* Cookies de session et de transaction OIDC paramétrés par provider.
* `loginHandlers` indexés par host, `serveMCPProtectedResourceMetadata` par
  access unit/provider.
* `Reloadable` : nouvelle génération construite avec providers dégradés,
  swap, drainage, puis `Close()` des anciens providers.
* `Gateway.Close()` ferme les stores, les clients HTTP et les providers.

  unitaires de Gate One.

Le broker de test expose `Down`, `FailJWKS`, `FailToken`, `RotateKey`, `Slow`,
`Revoke(sid)`.

== 6. Détail des tests

=== AC-AUTH-01 — Login Google

`TestAC_AUTH_01_GoogleLoginCreatesSession`

Étapes :

. Démarrer faux Google, broker de test, Gate One avec le provider `acme`.
. `GET /` sur `app.acme.test` sans cookie.
. Suivre la redirection vers le broker puis Google.
. Google auto-consent, callback broker, callback Gate One.
. Vérifier le cookie de session, `roles`, `tenant`, `sid`.

Assertions :

* `200` sur la page protégée ;
* cookie `cladone_acme_session` présent, `HttpOnly`, `Secure`, `SameSite=Lax` ;
* claims `tenant=acme`, `roles` attendus, `sid` non vide ;
* aucun cookie Google sur le domaine Gate One ;
* le broker n'a jamais transmis le token Google à Gate One.

Sous-tests :

* `google_consent_ok` ;
* `workspace_hd_required` ;
* `email_unverified_rejected` ;
* `wrong_nonce_rejected` ;
* `wrong_state_rejected` ;
* `pkce_required`.

=== AC-AUTH-02 — Cross-tenant

`TestAC_AUTH_02_CrossTenantTokenRejected`

Table :

|===
| Token | Route | Attendu

| `iss=acme`, `aud=acme` | `contoso` | `401`
| `iss=contoso`, `aud=contoso` | `acme` | `401`

Le test vérifie aussi que le cache d'identité n'est pas partagé : deux providers
de même type `oidc` ne doivent pas avoir la même clé de cache.

=== AC-AUTH-03 — Validation locale

`TestAC_AUTH_03_MCPValidationUsesJWKSOnly`

* Premier appel MCP : un fetch JWKS est autorisé.
* Appels suivants avec le même `kid` : `CountingTransport` doit montrer **zéro**
  appel au broker.
* Le broker est ensuite arrêté ; le token encore valide doit continuer à passer.
* Un token avec `kid` inconnu doit provoquer un fetch ; si le broker est down,
  `502`.

=== AC-AUTH-04 — Rotation de clé

`TestAC_AUTH_04_KeyRotationKeepsSessions`

* Émettre un token avec `kid=acme-2026-01`.
* Publier `acme-2026-02` dans JWKS.
* Émettre un nouveau token avec `acme-2026-02`.
* Vérifier que l'ancien et le nouveau token sont acceptés pendant le chevauchement.
* Avancer l'horloge au-delà de l'expiration de l'ancien token.
* Retirer `acme-2026-01` du JWKS.
* Vérifier qu'aucune session Gate One n'est déconnectée par la rotation.

Sous-tests :

* `old_token_valid_during_overlap` ;
* `new_kid_triggers_refresh` ;
* `old_key_retired_after_ttl` ;
* `rotation_does_not_clear_session_cookie`.

=== AC-AUTH-05 — Back-channel logout

`TestAC_AUTH_05_BackchannelLogoutRevokesSession`

* Login, récupérer `sid`.
* Broker envoie un logout token signé à `/backchannel-logout`.
* Vérifier le store de révocation.
* Prochaine requête avec le cookie : `401`.
* Le cache d'identité est invalidé.
* Un logout token rejoué est idempotent.
* Un logout token mal signé est refusé sans révocation.

=== AC-AUTH-06 — Mode dégradé par tenant

`TestAC_AUTH_06_BrokerDownDegradesOnlyTenant`

Scénario :

. Deux tenants `acme` et `contoso`, deux brokers.
. Login sur les deux.
. Arrêter le broker `acme`.
. Requête avec session `acme` : `200` (validation locale).
. Nouveau login `acme` : `502`.
. MCP `acme` avec `kid` en cache : `200`.
. MCP `acme` avec `kid` inconnu : `502`.
. Routes `contoso` : `200`.
. `/healthz` : `200`.
. `/readyz` : `200` car `contoso` sert encore.
. `/__gate-one/health/providers` : `acme=degraded`, `contoso=ready`.

=== AC-AUTH-11 — Enrichissement optionnel

`TestAC_AUTH_11_EnrichmentOptional`

=== AC-AUTH-14 — Token invalide vs indisponible

| JWKS 500 | `ErrProviderUnavailable` | `502`
| JWKS timeout | `ErrProviderUnavailable` | `502`
| JWKS malformé | `ErrProviderUnavailable` | `502`
| `kid` inconnu + refresh OK + token invalide | `ErrUnauthenticated` | `401`
| `kid` inconnu + refresh KO | `ErrProviderUnavailable` | `502`
| store de révocation en erreur | `ErrProviderUnavailable` | `502`
| session existante, broker down | aucune erreur | `200`
| nouveau login, broker down | `ErrProviderUnavailable` | `502`
|===

Le test vérifie aussi les en-têtes : `WWW-Authenticate` uniquement sur `401`.

=== AC-AUTH-15 — Démarrage/reload dégradé

`TestAC_AUTH_15_DegradedStartupAndReload`

* Démarrage avec `acme` down, `contoso` up : process démarre ; `acme` `degraded`,
  `contoso` `ready` ; routes `contoso` `200`.
* Reload avec `acme` down : nouvelle génération ; `acme` `degraded` ; `contoso`
  mise à jour.
* Reload avec config invalide : refusé ; ancienne génération active.
* Reload avec un provider qui revient : `acme` repasse `ready` après health check.
* Drain : les requêtes en cours sur l'ancienne génération se terminent.

=== AC-AUTH-16 — Plugin V2

`TestAC_AUTH_16_PluginManifestV2`

* manifeste valide + signature valide + digest valide → chargé ;
* clé inconnue → refus ;
* signature invalide → refus ;
* digest mismatch → refus ;
* `hostAPI` incompatible → refus ;
* dépendance manquante → refus ;
* digest révoqué → refus ;
* capability `auth` dans un plugin de route → refus ;
* downgrade vers une version vulnérable → refus.

=== AC-AUTH-17 — Pas de fuite de secret

`TestAC_AUTH_17_NoSecretLeak`

* Capturer les logs et les corps d'erreur.
* Vérifier l'absence de token, code, mot de passe, clé privée, secret client.
* Vérifier que les erreurs `502` ne contiennent pas l'URL interne complète si elle
  contient des credentials.
* Vérifier que `-check` ne sérialise pas les secrets.

=== 12.3 Statuts HTTP

[cols="2,1,2"]
|===
| Cas | Statut | Login proposé

| token absent/invalide/expiré | `401` | oui (navigation)
| scope insuffisant | `403` | non
| identity refusée | `403` | non
| provider/JWKS/store indisponible | `502` | non
| config invalide | — | démarrage/reload refusé
| rate limit | `429` | non
|===

=== 12.4 Glossaire

* **Provider** : configuration Gate One d'un émetteur OIDC/JWT.
* **Broker** : service qui fédère les IdP et ré-émet des JWT.
* **IdentityAdapter** : contrat interne du broker pour un protocole d'IdP.
* **Tenant** : domaine d'isolation (issuer, clé, audience, cookies, store).
* **Fail-fast par tenant** : la panne d'un provider dégrade ses routes, pas les
  autres tenants.
* **Token invalide** : le client peut corriger (`401`).
* **Provider indisponible** : Gate One ne peut pas vérifier (`502`).

=== 13.2 Limites connues

* Le broker utilise Redis quand `redis` est configuré ; sinon le store
  mémoire reste le défaut de test/dev. En production multi-instance,
  Redis est requis.
* Le binding gRPC n'est pas encore implémenté ; le contrat et le binding
  HTTP sont prêts.
* Les tests de staging (vrai Google, navigateurs, charge, chaos) ne sont
  pas automatisés dans ce dépôt.
* Le mode dégradé couvre le démarrage, le reload et la panne runtime.
* L'E2E navigateur complet Gate One <-> broker (cookie de domaine,
  redirections réelles) n'est pas automatisé dans ce dépôt : les briques
  sont testées séparément (broker fake Google, OIDC wiring, JWT/JWKS).
  Le staging avec vrai Google reste la validation finale.
