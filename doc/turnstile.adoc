= Cloudflare Turnstile bot check
:toc: left
:toclevels: 3

Gate One can protect form pages with Cloudflare Turnstile. The block is
**platform-wide**: one place in the configuration, every matching page
gets the widget, and every matching POST is verified before the backend
sees it. It works on pages Gate One already proxies, without changing
the application.

== What it does

. On an HTML page whose path matches, Gate One injects a small script
  before `</body>`.
. The script renders the Turnstile widget in every matching form and
  keeps the hidden `cf-turnstile-response` input in sync.
. A matching POST is verified with the Cloudflare **Siteverify** API
  before the backend; a missing, expired or invalid token is refused.

== What it does not do

This feature protects **only traffic that passes through this Gate One
instance**. It is not a replacement for network isolation:

* a second ingress (nginx, Traefik, Kubernetes Ingress, another Gate One
  deployment with a different configuration) that reaches the
  application directly **bypasses** the check;
* internal callers, batch jobs and a published container port bypass it
  too.

The invariant is: **the application is reachable only through the
verification point**. In practice, restrict the application's network
access to the Gate One instance (or its sidecar) and deny everything
else. Adding the check in Gate One does not create that isolation.

A global block also avoids the other bypass: forgetting the policy on one
host or one route of the same instance. It does not help across separate
configurations.

== Configuration

[source,json]
----
{
  "turnstile": {
    "enabled": true,
    "siteKey": "0x4AAAAAAA...",
    "secretEnv": "TURNSTILE_SECRET",
    "hosts": ["app.example.com"],
    "paths": ["/contact/*", "/register"],
    "methods": ["POST"],
    "forms": ["form#contact", "form[data-turnstile]"],
    "action": "contact",
    "hostname": "app.example.com"
  }
}
----

[cols="1,2,1",options="header"]
|===
| Field | Meaning | Default

| `enabled` | Explicit switch for templated configs. Absent = enabled
when the block is present. | true
| `siteKey` | Public widget key. Cloudflare binds it to a domain list:
declare every public hostname. | required
| `secretEnv` | Environment variable holding the secret key. The secret
is never read from the file and never sent to the browser. | required
| `hosts` | Exact hostnames or a leading `*.` wildcard. Empty = every
route. | all
| `paths` | Route-path grammar: `/contact/*` (prefix on a path
boundary), an exact path, `/*`. Empty = every path. | all
| `methods` | Verified methods: `POST`, `PUT`, `PATCH`, `DELETE`. | POST
| `forms` | CSS selectors of the forms receiving the widget. Empty =
every POST form. | all POST forms
| `action` | Optional action sent with the widget and required in the
Siteverify answer (1-32 chars: letters, digits, `_`, `-`). | none
| `hostname` | Optional expected hostname in the Siteverify answer. |
none
| `tokenHeader` | Header accepted in addition to the form field, for
fetch/SPA clients. | `X-Turnstile-Response`
|===

The secret must be present on **every replica** (same value) and is read
at startup: a missing variable refuses to start instead of silently
disabling the check.

[source,bash]
----
export TURNSTILE_SECRET=...
gate-one -check -config api-routes.json
----

== Injection behaviour

The injected script is a normal Gate One injection:

* only `frontend` routes returning HTML are modified; JSON, assets and
  redirects are untouched;
* it runs once per page, before `</body>`;
* it renders only into forms whose method is POST (a form without
  `method` defaults to GET and is skipped);
* with `forms` empty, every POST form is covered; with selectors, only
  the matching forms;
* a form marked `data-gtw-turnstile="off"` is always skipped;
* dynamically added forms (SPA) are picked up by a debounced
  `MutationObserver`;
* submitting before the widget resolves is blocked client-side, and the
  widget is scrolled into view — the token is the server's decision, the
  script only makes the failure understandable;
* same-origin mutating `fetch` calls automatically carry the token in
  `tokenHeader`, so an SPA form needs no application change. A request
  that sets its own header wins.

The site key is public and appears in the page. Never put the **secret**
in an injection bundle: bundles are rendered to the browser.

== Verification

For every matching request, Gate One reads the token:

* from the configured header (`X-Turnstile-Response` by default), then
* from the body: `application/x-www-form-urlencoded`,
  `application/json` (key `cf-turnstile-response` or
  `cfTurnstileResponse`), or `multipart/form-data`.

It calls Siteverify with the secret, the token and the client IP (last
`X-Forwarded-For` hop, like the rate limiter), then checks:

* `success` (Cloudflare's decision);
* `hostname` when configured;
* `action` when configured.

Tokens are **single-use** and expire after 300 seconds: never retry
Siteverify with the same token, and never verify it a second time in the
backend. Gate One consumes the token; the application must not call
Siteverify for the same submission.

The check runs **after** the rate limit (a flood does not burn Siteverify
calls) and **before** the backend, delegated credentials and forwarding.
The token and the secret are never logged and never written to usage
events.

== Failure modes

[cols="1,1,2",options="header"]
|===
| Situation | Status | Body

| Missing token | `403` | readable page for a navigation, `{"error":"turnstile_failed"}` otherwise
| Invalid / expired token | `403` | same, with an "expired" message when Cloudflare says `timeout-or-duplicate`
| Hostname mismatch (configured) | `403` | same
| Action mismatch (configured) | `403` | same
| Siteverify unreachable, timeout or non-200 | `503` | readable page / `{"error":"turnstile_unavailable"}`, `Retry-After: 5`
|===

A Siteverify outage is deliberately **not** a 403: telling a human "you
failed the robot check" because Cloudflare is down would be wrong. It is
fail-closed (the backend is never reached) with a distinct error.

== Content Security Policy

Turnstile needs two origins in the page's policy:

* `script-src` (and `script-src-elem` when declared) must allow
  `https://challenges.cloudflare.com`;
* `frame-src` must allow `https://challenges.cloudflare.com`.

When a route declares a `csp` block, Gate One appends those sources to
the directive the browser actually uses, in all modes:

* `nonce`/`hash`: added to the emitted policy;
* `merge`: appended to the origin's policy (a union — no source is
  removed);
* a directive absent with a `default-src` fallback is widened there;
* with no directive and no `default-src`, the browser imposes no
  restriction and nothing is added (adding a restrictive directive would
  break the page).

The inline loader script is nonced or hashed by the existing CSP
machinery. Without a `csp` block on the route, Gate One adds no policy and
the page's own CSP (if any) must allow the two origins.

Pre-clearance mode additionally needs `connect-src 'self'`; this block
does not enable pre-clearance.

== Local testing

Cloudflare publishes test keys:

[cols="1,2",options="header"]
|===
| Key | Value

| Always-passing site key | `1x00000000000000000000AA`
| Always-blocking site key | `2x00000000000000000000AB`
| Always-passing secret | `1x0000000000000000000000000000000AA`
| Always-failing secret | `2x0000000000000000000000000000000AA`
|===

Use them in a development configuration; production keys reject the
dummy tokens.

== Operational notes

* **Secret**: one per widget, same on every replica, rotated in the
  Cloudflare dashboard and the environment.
* **Rate limit**: keep a `rateLimit` on the protected route; it runs
  before Siteverify.
* **Privacy**: the client IP is sent to Cloudflare for validation.
  Mention it in the privacy notice; it is the same data Cloudflare
  already sees if the site is behind its edge.
* **Rolling restart**: a configuration reload (`SIGHUP`) recreates the
  gateway, including the Turnstile runtime; an invalid block is refused
  and the previous configuration stays active.
* **Monitoring**: `TURNSTILE ... result=ok|missing|failed|unavailable`
  log lines carry the host and path, never the token. A spike in
  `unavailable` means the Siteverify dependency is degraded.

== When not to use it

* For an authenticated area: Gate One's SSO is a stronger control; a
  bot cannot log in.
* As a substitute for network isolation: see the limitation above.
* On a form whose backend already implements Siteverify: verify in one
  place only (the token is single-use).
